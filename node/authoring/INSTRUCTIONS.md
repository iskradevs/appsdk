# Каркас приложения Искры

Начинай с ближайшего целого примера в `examples/` и сохраняй его модульную
структуру. Задай `<slug>`, `<version>`, экран, HTTP-маршруты и нужное хранение.
`src/server.ts` запускает сервер и подключает маршруты; `src/config.ts` задаёт
имя и стиль; `routes.ts` обрабатывает HTTP; `views.ts` строит HTML;
`service.ts`, `data.ts` или `storage.ts` выполняют операции с данными.
Для простого приложения оставляй только нужные модули. Браузерный JavaScript
размещай отдельными файлами в `static/`.

1. Начинай с `iskra-app init --name <slug> --layout <id>` либо ближайшего
   примера в `examples/layouts/` (`form`, `table`, `dashboard`,
   `master-detail`, `sidebar`, `wizard`); для сервера без макета подойдут
   `examples/minimal`, `interactive` и `stateful`.
2. Замени `name` и `version` в `app.json`; `entry`, `health` и `storage` уже
   согласованы с платформой.
3. Сохрани `GET /healthz`, обслуживай UI под `appBasePath()` и не добавляй
   собственный runtime. Корневой роутер создавай как
   `new Hono({ strict: false })`: узел проверяет кандидата запросом в корень
   приложения СО слэшем (`/{slug}/`) и туда же водит зрителей, а строгий роутер
   Hono считает `/{slug}` и `/{slug}/` разными путями и отвечает пробе 404 —
   версия не публикуется. Адрес `{slug}` приложению задаёт платформа и меняет
   при переименовании: путь бери из `appBasePath()`, а для локального прогона
   ставь в `APP_BASE_PATH` адрес из ответа `publish_app` (поле `slug`) или
   карточки приложения — `name` из `app.json` адрес не задаёт.
4. Собери без сети: `iskra-app pack --closed --path <dir> --output <app.zip>`.
5. Сразу после runtime pack сохрани переносимые авторские исходники:
   `iskra-app source-pack --path <dir> --output /workspace/<slug>-source.zip`.
6. Проверь именно runtime zip: в одном shell распакуй его в собственный
   временный каталог, запусти сервер с cwd этого каталога, проверь `/healthz`,
   корень приложения с завершающим `/`, браузерные файлы и основной путь.
   Останови процесс и очисти свои временные каталоги до конца этого shell.
7. Передай runtime zip в `publish_app`; исправляй код только по результату этой
   проверки. Новое приложение создаётся этим вызовом: передай подтверждённое
   название в `title` (до 80 символов) — его увидит пользователь в разделе
   «Приложения». Публикация в уже созданное приложение (в том числе в черновик
   из раздела) идёт с его `app_id`, а название приложения приходит в ответе.

`pack` и `publish` собирают runtime во временном staging и очищают его после
завершения. Авторский проект сохраняет один `app.json` и исходные модули.
Явный `build` создаёт `.iskra-build` для ручной работы; при следующем успешном
pack SDK убирает этот каталог после проверки состава и манифеста того же
приложения. Неизвестное содержимое даёт исправимую ошибку с сохранением файлов.
Редактируй авторские модули и `app.json`, затем заново создавай runtime ZIP.

Source archive включает только `app.json`, `src/**` и опциональный `static/**`.
Сегменты `.env*`, `node_modules` и `.iskra-build` исключаются на любой глубине.
Абсолютный output должен находиться вне каталога проекта: тогда antrunner
синхронизирует artifact в файловую панель чата.
В Linux `source-pack` восстанавливает путь временного файла через
`/proc/self/fd`; на macOS и Windows проверяет исходный путь по совпадению
`dev`/`ino`/`size`. Подменённый путь команда не удаляет. До завершения команды
`/workspace` должен оставаться смонтированным стабильным родительским каталогом
output: не перемещай и не заменяй его.

`publish_app` доступен только на контуре с `APPS_RUNTIME_ENABLED=true`: без узла
и browser-гейта публикация из чата намеренно не рекламируется.

Результат публикации имеет `state=ready|ready_not_active|probing`.
`ready` означает успешную browser-проверку; фактическую активацию всегда читай
из `activated` и `current_version` (при `activate:false` версия останется ready,
но не станет текущей).
`ready_not_active` означает, что browser-проверка прошла, но версия не стала
текущей (например, ждёт публичного одобрения). `probing` сохраняет `app_id` и
`version`: проверка ещё идёт, поэтому не публикуй тот же номер повторно.

В chat build разрешены `@iskra/apps`, `@hono/node-server`, `hono`, `zod` и
встроенные модули Node 24. Секреты объявляются слотами манифеста, но никогда не
записываются в исходники или бандл. Relative imports остаются внутри real root
проекта; absolute paths и обход через symlink закрытая сборка отклоняет.
Пользовательский путь прямо в `node_modules` также запрещён, включая обход
через symlink и symlink entrypoint: зависимости подключаются только разрешённым
bare import.

Для интеллекта вызывай `client.run(input, { idempotencyKey })`: создай один
ключ для пользовательского действия и передавай его вместе с тем же payload
при сетевых повторах. Для следующего действия, включая продолжение после
`interaction_required`, создай новый ключ. Метод возвращает union
`completed|interaction_required`. Проверяй `isInteractionRequired(result)` и
показывай пользователю реальные snake_case поля
`interaction.tool_call_id`/`interaction.inputs`; для async polling передавай
`AbortSignal` в `progress`, чтобы отменялись и пауза, и текущий `getRun`.

## Оформление экранов

Экран собирается из общего слоя `@iskra/apps`: он даёт токены палитры Искры,
обе темы, шапку, карточки, кнопки, таблицы, поля формы, бейджи, строку
состояния и крутилку. Слой едет внутри бандла и пристёгнут к его версии.

```ts
import { APP_CSP, APP_STYLESHEET_PATH, appPage, appStylesheetResponse, appTitle } from "@iskra/apps";

ui.use("*", async (context, next) => {
  await next();
  context.header("Content-Security-Policy", APP_CSP);
});
ui.get(`/${APP_STYLESHEET_PATH}`, (context) => appStylesheetResponse(context.req.raw));
ui.get("/", (context) => context.html(appPage({ title: appTitle(context.req.raw, "invoices"), body, request: context.req.raw })));
```

Название экрана бери из `appTitle(context.req.raw, fallback)`: роутер передаёт
название, которое владелец задал на платформе, заголовком `x-iskra-app-title`
(percent-encoded UTF-8), и правка названия доезжает до зрителей без
пересборки. В `fallback` передавай `name` из `app.json` (в сниппете —
`invoices`): его видят проба узла и локальный запуск, которые идут мимо
роутера.

Разметку пиши обычную: `main`, `table`, `button`, `input` оформлены сами.
Классы уточняют раскладку — `card card--pad` для блока, `page--wide` для
широкой таблицы, `btn-primary` для главного действия экрана и `btn-danger` для
разрушительного, `toolbar` для строки кнопок со `status` справа,
`fields-grid`/`field`/`field__label` для формы, `stack` для вертикальной
стопки, `badge badge--accent|--success|--danger` для состояния в таблице,
`num` для числовой колонки, `is-empty` для незаполненного поля, `empty` для
пустого списка, `hint` для пояснения. Строка состояния меняет вид классом:
`status status--ok|--warn|--error`.

### Шапка, стиль и макеты

`appPage` рисует шапку Iskra Apps: бренд, название экрана, навигацию и имя
зрителя. Передай `request: context.req.raw` — роутер кладёт в запрос адрес
раздела «Приложения» и имя зрителя (заголовки `x-iskra-home-url` и
`x-iskra-viewer-name`), и шапка показывает бренд ссылкой на раздел и зрителя
с аватаром. Без `request` шапка показывает бренд без ссылки и без зрителя:
так выглядит проба узла и локальный запуск. У уже опубликованного приложения
новая шапка появится после пересборки и повторной публикации версии: слой
оформления пристёгнут к бандлу.

Стиль выбирается параметром `style` (значения — `APP_STYLES`) и записывается
атрибутом `data-style` на `<html>`; стиль меняет токены (у «Витрины» ещё засечки в заголовках), компоненты
одни на все стили:

| `style` | Характер |
|---|---|
| `iskra` (по умолчанию) | палитра Искры; атрибут не пишется |
| `strict` | плотный и холодный серо-синий, тёмная шапка, малый радиус: учёт и отчёты |
| `showcase` | крупный, тёплый фон, большой радиус, засечки в заголовках, коралловый акцент: для клиентов |

Меню слева включается так: `navPosition: "side"` и `nav` со ссылками, у
текущего раздела `current: true` (он получает `aria-current="page"`).
Разделы удобно держать в одном маршруте через `?section=<ключ>`. При пустом
`nav` меню слева не рисуется.

Классы раскладок: `kpis`/`kpi`/`kpi__label`/`kpi__value` — плитки цифр;
`split` — список рядом с карточкой (на узком экране одна колонка);
`list-select`/`list-select__item` — выбираемый список, выбранная строка
помечается `aria-current="true"`; `steps`/`step`/`step--done` — шаги мастера;
`table-wrap` — обёртка таблицы в карточке; `section__title` — заголовок блока.

| Макет | Для чего | Опора в примере |
|---|---|---|
| `form` | ввод данных и отправка | `fields-grid`, `status` |
| `table` | реестр записей | `table-wrap`, `toolbar`, `badge`, `num` |
| `dashboard` | сводка цифр | `kpis`, `kpi`, таблица |
| `master-detail` | список и карточка записи | `split`, `list-select` |
| `sidebar` | несколько разделов с меню слева | `navPosition: "side"`, `?section=` |
| `wizard` | многошаговый сценарий | `steps`, `step--done` |

Готовые примеры лежат в `examples/layouts/<id>/`. Команда
`iskra-app init --name <slug> --layout <id> --style <id>` копирует макет в
проект с нужным именем и стилем; без `--layout` создаётся минимальный каркас,
без `--style` берётся `iskra`.

Собственный CSS-файл добавляй в `static/` поверх общего слоя и подключай через
`head` в `appPage` — там живёт частное этого приложения (ширины колонок,
раскладка конкретного экрана). Значения бери из токенов слоя (`var(--accent)`,
`var(--surface)`, `var(--border)`), тогда обе темы работают сами.

Код экрана отдавай отдельным маршрутом с `content-type: text/javascript` и
подключай через `<script src="…" defer>`: политика содержимого применима к
каждому экрану, а встроенный блок она отменяет, и browser-гейт публикации
видит ошибку в консоли. Данные, пришедшие из внешней системы, вставляй в
разметку через `escapeHTML`.

Для браузерного файла используй свой static-маршрут, например
`ui.get("/screen.js", serveStatic({ root: "./static", path: "screen.js" }))`
из `@hono/node-server/serve-static`. Фиксированный `path` отображает адрес
`/<slug>/screen.js` на `static/screen.js` относительно cwd runtime.
